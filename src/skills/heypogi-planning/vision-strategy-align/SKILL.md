# Vision / Strategy Alignment

Verify that a repo's two grounding documents work together as one source of truth:

- **`VISION.md`** — operator-authored, canonical product definition. What the product is and why it must exist.
- **`STRATEGY.md`** — derived strategic framing (typically generated by the CE plugin's `ce-strategy` skill). How we win and where we invest.

**Precedence rule: VISION.md governs.** STRATEGY.md is a derivation, never a second source of truth. When they conflict, the strategy is wrong until the operator says otherwise.

## Why this skill exists

The CE plugin's `ce-strategy` skill has **no concept of an upstream vision document** — it interviews the operator from scratch and never reads `VISION.md`. Nothing in CE enforces vision→strategy consistency, and CE's downstream skills consume STRATEGY.md directly: `ce-plan` reads Target problem, Our approach, and Tracks; `ce-brainstorm` and `ce-ideate` read the whole doc for product direction; `ce-dogfood` reads Who it's for; `ce-product-pulse` re-reads Key metrics on every run. A drifted STRATEGY.md silently poisons planning, ideation, and QA — so alignment must be checked deliberately. That is this skill's job.

## Trigger conditions

- `VISION.md` was created or edited
- `STRATEGY.md` was created, regenerated, or updated (e.g., a `ce-strategy` run just finished)
- A planning or brainstorming phase is about to start and both documents exist
- User asks to check alignment, drift, or consistency between vision and strategy

## Step 1 — Locate the documents

Look for `VISION.md` and `STRATEGY.md` at the repo root.

- **Both present** → continue to Step 2.
- **Only VISION.md** → no alignment to check. Note that `ce-strategy` can derive a strategy, and that its interview answers should come from VISION.md's content (see "Working with ce-strategy" below). Still run Step 4 (scaffold check).
- **Only STRATEGY.md** → flag it: the strategy has no canonical product definition anchoring it. Ask the operator whether a vision document exists elsewhere or should be written first. Still run Step 4.
- **Neither** → tell the user this skill has nothing to check; stop after offering Step 4 if agent instructions exist.

## Step 2 — Run the alignment rubric

Six checks, each pass/fail with evidence (quote or line reference). Use the ownership matrix below as the standard for checks 3 and 5.

| # | Check | Pass condition |
|---|---|---|
| 1 | **Derivation header** | STRATEGY.md explicitly declares it is derived from VISION.md and that VISION.md governs conflicts (e.g., "Derived from `VISION.md`, the canonical product definition. If the documents conflict, `VISION.md` governs.") |
| 2 | **Traceability** | Every STRATEGY claim maps to a VISION anchor: Target problem ↔ Problem; Our approach ↔ the vision's core design bet; Who it's for ↔ Who it's for; each Key metric ↔ a success criterion; each Track ↔ a vision section it serves; Not working on ⊆ Out of scope. Any STRATEGY statement with no VISION anchor = drift. |
| 3 | **No new scope** | STRATEGY introduces no capability, user, requirement, or exclusion absent from VISION. |
| 4 | **No contradiction** | Pairwise check of audience, problem framing, and scope boundaries finds no direct conflict. Any conflict = fail; VISION governs; escalate to operator. |
| 5 | **Ownership** | No information lives in the wrong document per the ownership matrix. Common violations: features/schedules/roadmaps in either doc; product behavior restated in STRATEGY; current metric *values* (vs definitions) in STRATEGY; measurable metrics in VISION. |
| 6 | **Freshness** | VISION.md's last modification (git log) is not newer than STRATEGY.md's `last_updated` frontmatter. If VISION changed after the strategy was last touched, flag for re-derivation review. Do not assume CE polices this — no downstream CE skill implements a staleness check. |

### Ownership matrix

One home per information type. Overlap is allowed only as *derivation* — STRATEGY restating VISION content in strategy-kernel form — never as a second source of truth.

| Information type | Owner | The other doc may... |
|---|---|---|
| Problem statement (what's broken, for whom) | VISION | STRATEGY compresses it into **Target problem** (diagnosis only, no solution language) |
| Product behavior (what it does, lifecycle, authority boundaries) | VISION | STRATEGY never restates behavior |
| Audience / users | VISION | STRATEGY sharpens into **Who it's for** (persona + jobs-to-be-done) |
| Core bet / mechanism of winning | VISION (implicitly, as the design) | STRATEGY makes it explicit as **Our approach** — a choice that rules out alternatives |
| Success criteria (qualitative, definitional) | VISION | STRATEGY derives 3–5 **Key metrics** (measurable, with measurement source) |
| Scope exclusions | VISION (**Out of scope**) | STRATEGY's **Not working on** must be a subset — never a new exclusion |
| Investment areas / where effort goes | STRATEGY (**Tracks**) | VISION doesn't sequence or prioritize |
| Measurable metrics + where measured | STRATEGY | VISION stays qualitative |
| Features, requirements, plans, schedules | **Neither** — brainstorm docs, plans, issue tracker | Both docs stay clean |

Litmus test: if a sentence answers "what does the product do?" it belongs in VISION; if it answers "where do we focus and how do we know it's working?" it belongs in STRATEGY.

## Step 3 — Report

Produce a short report:

```markdown
## Vision/Strategy alignment check

| # | Check | Result | Evidence |
|---|-------|--------|----------|
| 1 | Derivation header | pass | STRATEGY.md:8 |
| 2 | Traceability | fail | Track "X" has no VISION anchor |
| ... | | | |

**Verdict:** aligned | drifted (list items) | conflicted (VISION governs — operator decision needed)
```

Verdict meanings:

- **Aligned** — all six checks pass.
- **Drifted** — no direct contradiction, but traceability, scope, ownership, or freshness failures exist. List each with a suggested fix.
- **Conflicted** — the documents disagree. VISION.md governs. Present the conflict to the operator; do not proceed with planning work grounded in the conflicted content.

**Never silently edit either document to resolve a finding.** Report first. Apply fixes only when the operator approves, and fix STRATEGY.md to match VISION.md — not the reverse — unless the operator explicitly rules the vision is what changed.

## Step 4 — Verify the repo's agent instructions carry the convention

Read the repo's agent instructions file — `AGENTS.md`, falling back to `CLAUDE.md` (check both root and any referenced instruction files).

Check for two things:

1. **A precedence statement** — something equivalent to "VISION.md is canonical; STRATEGY.md is derived; VISION.md governs conflicts."
2. **A check trigger** — an instruction to run this alignment check (or an equivalent rubric) whenever either document changes.

If **both** are present, say so and finish.

If **either is missing**, tell the user what's missing and why it matters:

> Your agent instructions don't tell agents that VISION.md governs STRATEGY.md (or when to check alignment). Without this, any agent session — including CE skills like ce-strategy, ce-brainstorm, and ce-plan — can regenerate or consume STRATEGY.md with no obligation to stay faithful to the vision, and drift will accumulate silently across sessions. The convention only works if every session inherits it from the instructions file.

Then **ask the user** whether they want the instructions updated. If yes, add a compact block like this (adapt wording to the file's existing style; do not duplicate anything already there):

```markdown
- `VISION.md` is the canonical product definition; `STRATEGY.md` is derived from it
  and must not conflict with it, introduce new scope, or restate product behavior.
  If they conflict, `VISION.md` governs — surface the drift to the operator.
- After either `VISION.md` or `STRATEGY.md` changes, run the `vision-strategy-align`
  skill and report the verdict before continuing with planning or implementation work.
```

If no, respect the decision and note the residual risk in one sentence.

## Working with ce-strategy

When a repo has a `VISION.md` and the user runs `ce-strategy` (create or update):

- Answer the ce-strategy interview *from VISION.md's content* — its problem statement, audience, design bet, success criteria, and scope exclusions — rather than improvising new answers.
- After ce-strategy writes or updates STRATEGY.md, run this skill's rubric on the output before treating the strategy as grounding.

## Boundaries

- This skill checks and reports; it edits documents only with explicit operator approval.
- It does not author visions (operator's job) or strategies (`ce-strategy`'s job).
- It does not review general document quality — use `ce-doc-review` or `clarity-without-drift` for that.
- The rubric assumes CE's locked STRATEGY.md template (Target problem, Our approach, Who it's for, Key metrics, Tracks, plus optional Milestones / Not working on / Marketing). For a non-CE strategy doc, map sections by purpose and note the deviation in the report.
